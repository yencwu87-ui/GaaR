# v0.8.1 Hardening Notes — Deterministic Governance Basis

This patch tightens the v0.8 governance decision engine without changing the human-accountable decision model.

## Corrections

- **Strong challenge blocker is strength-specific.** `STRONG_CHALLENGE_UNRESOLVED` now fires only when an actually strong challenge is unresolved. Resolved strong challenges and unrelated weak unresolved challenges no longer combine into a false blocker. Explicit `accepted`/`rejected` resolution takes precedence over stale open/pending status.
- **Basis hashing is canonical and reproducible.** Governance basis serialization now uses sorted-key JSON, compact separators, UTF-8, and the full SHA-256 digest. Unexpected non-JSON values fail closed instead of being silently converted with `default=str`.
- **Basis collections are canonically ordered.** Latest claim assessments are keyed in claim-id order; challenges are ordered by `challenge_id`/`id`; probes are ordered by `probe_id`/`id`.
- **Longitudinal precedent is event-order aware.** Event projections now preserve the decided event timestamp, event id, and global event sequence index. Precedent analysis uses that sequence rather than assuming caller-provided history is already chronological.
- **Append-only decision event remains sufficient for replay.** `decide()` already persists the complete `governance_decision`, including posture, blockers, escalations, signals, precedent, summaries, basis object, and `basis_hash`, before recording the `decided` event. `enforce()` is called immediately before that append, at the cycle API boundary.

## Non-changes

- Contradicted governed claims still block a `full` decision regardless of materiality. Step/control-scoped materiality remains a future refinement.
- `escalate` remains a governed posture rather than a hard recording prohibition. A downstream workflow may treat it as a required routing state.

The broader repository suite remains time-consuming and was not represented as fully passing in this patch.
