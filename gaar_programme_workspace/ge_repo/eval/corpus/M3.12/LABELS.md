## Boundary for this control

**Defined in `requirements/mas.yaml` under `controls.M3.12`, not here.** That file is what
the assessor is judged against and what a reviewer reads. Restating it here created two
definitions of `full` for one control and they diverged. Reproduced below for reading
convenience only; if the two disagree, the requirement file wins and these labels must be
re-argued.

**Requirement.** AI and model changes are controlled through documented impact assessment,
testing, approval and traceability from change request through implementation and post-
implementation verification.

**Elements (6) — every applicable one must be evidenced for `full`:**

- `e0` — The change register is complete and internally consistent — no duplicate change ids, no unexplained gaps in the sequence, and entries current with the changes actually made *(lane b — tested deterministically, not scored here)*
- `e1` — Change categories, impact assessment, required testing and approval criteria are defined.
- `e2` — Change records link approval, implementation and the deployed system/version.
- `e3` — Post-implementation verification and closure or exception handling are required.
- `e3b` — The person who used that access is a named implementer on the approved change
- `e4` — Production state after implementation is verified against the approved plan, with deviations approved rather than closed silently

| Rating | Condition (from the requirement file) |
|---|---|
| full | All applicable requirement elements are evidenced with current, attributable and sufficient design or operating evidence; no material mandatory element remains unsubstantiated. |
| partial | Some applicable requirement elements are evidenced, but one or more required elements or operating evidence is missing or incomplete. |
| none | The control requirement is not evidenced beyond generic intent, policy aspiration or unrelated material. |

Maturity is judged separately and is not the label under test here.
